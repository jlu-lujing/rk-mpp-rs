# RK3576 / Luckfox Omni3576 adaptation

## Board baseline

- Board: Luckfox Omni3576
- DT compatible: `luckfox,omni3576`, `rockchip,rk3576`
- CPU: 8 cores, Linux 6.1.75
- Installed C MPP: 1.0.11, commit `4ed4f778`, 2025-09-10
- Video decoder: `27b00100.rkvdec` (`mpp_rkvdec2`)
- Video encoder: `27a00000.rkvenc-core`, `27a10000.rkvenc-core`,
  `rkvenc-ccu`
- Available DMA heap from userspace: `system`

## Codec blocks

The official MPP `soc.cmake` selects a different userspace HAL from RK3588:

| Capability | RK3588 / t6 | RK3576 / lf1 |
|---|---|---|
| H.264/H.265/VP9/AV1/AVS2 decode | VDPU34x | VDPU383 |
| H.264/H.265 encode | VEPU580 | VEPU510 |
| JPEG encode | VEPU2 path | VPU720 |
| video post-processing | integrated rkvdec path | VDPP2 |

The stock lf1 kernel/DTB does **not** expose VDPP client 29 in
`probe_hw_support`, so VDPP2 is a target of the SoC family but is not currently
drivable on this boot. A kernel/DTB that binds `vdpp2` is required before that
path can be implemented or validated.

The kernel client numbers remain shared. The register map and command offsets
do not: VDPU383 has a 276-word register window but different control/address
layout and syntax-table packing from VDPU34x. A successful `MppService::open`
therefore proves only that the kernel client bound, not that an RK3588 HAL can
run on RK3576.

Sources used for the mapping:

- `mpp/soc.cmake`, official MPP commit `9b56348`
- `osal/mpp_soc.c`, RK3576 SOC table
- `mpp/hal/rkdec/{h264d,h265d,vp9d,av1d}/*_vdpu383.c`
- `mpp/hal/rkenc/{h264e,h265e}/*_vepu510.c`
- `mpp/hal/rkenc/jpege/hal_jpege_vpu720.c`
- `mpp/hal/rkdec/inc/vdpu383_com.h`

## Rust VDPU383 H.264 bring-up

The first real Rust hardware path now passes on lf1:

- Stream: generated by ffmpeg/libx264, 640x480, 30 fps, 12 frames
- C oracle: stock C MPP 1.0.11, 12/12 frames
- Rust: debug build, 12/12 frames, 85-92 FPS across bring-up runs (not a
  performance claim)
- Plane output: byte-identical to C MPP
- SHA-256, both sides:
  `615ee129c46e10f7fb4cb2cf8af3cb370523f7605abee7e7315e073a4421b112`

The first two VDPU383 global-config and RPS blocks also match the C dumps
word-for-word. The bring-up established two RK3576-specific requirements:

- H.264 frame slots use the RK3576 704-byte stride for a 640-pixel width.
- VDPU383 colmv is the uncompressed 16-byte-unit map, and the global-config
  DPB flags/layer IDs share one 32-bit word. Adding a second zero word shifted
  subsequent P-picture POC/colmv state and produced `colmv_ref_error`.

The H.264 edge matrix is also **4/4**:

- 1280x720, 30 B-frame/H.264 frames: byte-identical to C MPP
- 1920x1080 hard stream, 90 frames: byte-identical to C MPP
- 720x480 PAFF, 15 frames: Rust matches FFmpeg; the stock lf1 C harness has a
  known field-order output difference
- 176x144 long-term-reference stream, 62 frames: byte-identical to C MPP

`scripts/board_rk3576_h264_edges_vs_mpp.sh` is the reproducible lf1 gate.

The WPP rows are not aliases for ordinary x265 output: `trace_headers` reports
`entropy_coding_sync_enabled_flag = 1` and five entry-point offsets. The 176-byte
VDPU383 global packet matches the patched C dump byte-for-byte and is pinned by
an offline FNV test. The packet carries the current and 15 reference POCs,
reference-valid bits, tile geometry and the VDPU383 RCB/address layout. The
H.264/H.265-specific RK3576 rules established here are:

- no-tile streams publish one column and one row to VDPU383;
- tile widths and heights are CTU counts, not `minus_one` values;
- `reg130` CABAC base is zero, `global_len` is `0xc`, and the RCB registers use
  offset/length pairs from the upper layout;
- scaling lists use 1360-byte slots selected by `sps_id` or
  `pps_id + 16`; the VDPU383 table stores all six 32x32 matrices in its
  block-column-major layout;
- the 176-byte H.265 packet is intentionally larger than the VDPU34x 112-byte
  packet and must not be negotiated as a variable payload.

This closes the H.265 core path with DSLICE and both scaling-list localities,
not the complete RK3576 H.265 surface. Long-term-reference/error injection and
the wider conformance matrix still need RK3576 runs.

## Rust VDPU383 VP9 bring-up

The VDPU383 VP9 matrix is **7/7** on lf1. The regular rows match the installed
C MPP byte-for-byte; the two known C defects retain the libvpx adjudication:

- profile 0 64x64, 12 frames
- profile 2 10-bit 64x64, 12 frames
- lossless 320x240, 12 frames
- profile 2 10-bit lossless 320x240, 12 frames
- error-resilient 2-column tiles, 640x360, 12 frames
- 720p error-resilient temporal segmentation: Rust == libvpx; C differs
- lossless 321x241: Rust/libvpx produce 2 frames; C produces 1

The bring-up established VDPU383-specific details. The 168-byte global header
is packed separately from the register file and the tile widths are CTU counts,
not `CTU count / 8`. The key-frame probability FIFO is 1312 bytes and the C
writer intentionally truncates the final zero-padded tail. RCB has eleven
VDPU383 regions with refined sizes, while `reg181`/`reg182` select the two
segment maps and the colmv buffer is the uncompressed `width * height / 2`
surface.

`scripts/board_rk3576_vp9_vs_mpp.sh` is the reproducible lf1 gate. The release
LTO compiler on lf1 currently SIGSEGVs in LLVM; the functional gate therefore
uses the debug build and makes no throughput claim.

## Rust capability parity scope

The acceptance target is the full official MPP capability surface exposed on
RK3576, not merely opening `/dev/mpp_service`:

| Path | Required implementation | Required evidence |
|---|---|---|
| H.264 decode | VDPU383 address/RCB/common registers, SPS/PPS/RPS/scan-list packing | byte-exact frames against C MPP |
| H.265 decode | VDPU383 address/RCB/common registers and HEVC table layout | byte-exact Main/Main10/tiles/WPP/720p/DSLICE/SPS-PPS-scaling matrix; LTR/error rows |
| VP9 decode | VDPU383 probability, segmentation and colmv lifetimes | byte-exact profile 0/2, 8/10-bit, lossless, tiles and known-C-bug adjudication |
| AV1 decode | VDPU383 PicParams/header/global-model and film-grain paths | byte-exact key/inter/film-grain matrix |
| AVS2 decode | VDPU383 AVS2 register path | conformance stream required before claiming support |
| H.264 encode | VEPU510 register/RC/GOP/ROI/slice/tile/STATUS paths | byte-identical streams and STATUS fields |
| H.265 encode | VEPU510 register/RC/GOP/ROI/slice/tile/STATUS paths | byte-identical streams and STATUS fields |
| JPEG encode | VPU720 packet and register path | byte-identical markers/packets |
| JPEG decode | RK3576 rkjpegd path | byte-exact output |
| VDPP2 | RK3576 post-processing command/register path | output comparison with C MPP |

Unsupported codec paths must be represented in the SoC capability matrix and
rejected before submission. They are not silently routed through VDPU2 or an
RK3588 register builder.
