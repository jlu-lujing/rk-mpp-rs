# RK3576 / Luckfox Omni3576 adaptation

## Board baseline

- Board: Luckfox Omni3576
- DT compatible: `luckfox,omni3576`, `rockchip,rk3576`
- CPU: 8 cores, Linux 6.1.75
- Installed C MPP: 1.0.11, commit `4ed4f778`, 2025-09-10
- Video decoder: `27b00100.rkvdec` (`mpp_rkvdec2`)
- Video encoder: `27a00000.rkvenc-core`, `27a10000.rkvenc-core`,
  `rkvenc-ccu`
- Available DMA heap from userspace: `system`

## Codec blocks

The official MPP `soc.cmake` selects a different userspace HAL from RK3588:

| Capability | RK3588 / t6 | RK3576 / lf1 |
|---|---|---|
| H.264/H.265/VP9/AV1/AVS2 decode | VDPU34x | VDPU383 |
| H.264/H.265 encode | VEPU580 | VEPU510 |
| JPEG encode | VEPU2 path | VPU720 |
| video post-processing | integrated rkvdec path | VDPP2 |

Both boards advertise their CCU topology through the device tree. The generic
`BatchServer` therefore detects the `rkvenc-ccu` node on lf1 and falls back to
one real-session poll after the shared `SET_SESSION_FD` submission. The
cross-session gate now covers both SoCs: two VEPU2 JPEG sessions on t6 and two
VEPU510 H.264 fixed-QP IDR sessions on lf1. Each board passes 3/3 with output
byte-identical to the corresponding standalone runs.

The stock lf1 kernel/DTB does **not** expose VDPP client 29 in
`probe_hw_support`, so VDPP2 is a target of the SoC family but is not currently
drivable on this boot. A kernel/DTB that binds `vdpp2` is required before that
path can run. The hardware-independent Rust port is nevertheless in place:
common/ZME scale, all four coefficient banks, default enhancement banks, the
10240-byte histogram parser and client-29 DMA-BUF submission match the vendor C
builder word-for-word in ten fake-service cells, including a non-default ZME
dering/blend profile, DMSR/ES/SHARP profiles and split Y/UV output. Pixel and histogram contents
remain unverified until the board runs a kernel/DTB that binds client 29.

The Rockchip `develop-6.1` source defines `vdpp@27961000` as
`rockchip,vdpp-rk3576` with `status = "disabled"` and enables it in
`rk3576-evb.dtsi` using only `&vdpp { status = "okay"; };`. This makes the lf1
blocker primarily a DTB-enablement issue, although `mpp_vdpp.c` must also be
built into that kernel.

`tools/rk3576-vdpp2-overlay.dts` enables the existing
`/iommu@27960800` and `/vdpp@27961000` nodes by target path. The opt-in
`scripts/board_enable_vdpp2_overlay.sh enable` uses configfs and can be reversed
with `disable`; it does not modify the boot image. Once client 29 binds,
`scripts/board_vdpp2_hw_vs_c.sh` compares scale-only, default enhancement,
packed histogram and mean luma against the C MPP source/library on the board.

The kernel client numbers remain shared. The register map and command offsets
do not: VDPU383 has a 276-word register window but different control/address
layout and syntax-table packing from VDPU34x. A successful `MppService::open`
therefore proves only that the kernel client bound, not that an RK3588 HAL can
run on RK3576.

Sources used for the mapping:

- `mpp/soc.cmake`, official MPP commit `9b56348`
- `osal/mpp_soc.c`, RK3576 SOC table
- `mpp/hal/rkdec/{h264d,h265d,vp9d,av1d}/*_vdpu383.c`
- `mpp/hal/rkenc/{h264e,h265e}/*_vepu510.c`
- `mpp/hal/rkenc/jpege/hal_jpege_vpu720.c`
- `mpp/hal/rkdec/inc/vdpu383_com.h`

The WPP rows are not aliases for ordinary x265 output: `trace_headers` reports
`entropy_coding_sync_enabled_flag = 1` and five entry-point offsets. The 176-byte
VDPU383 global packet matches the patched C dump byte-for-byte and is pinned by
an offline FNV test. The packet carries the current and 15 reference POCs,
reference-valid bits, tile geometry and the VDPU383 RCB/address layout. The
H.264/H.265-specific RK3576 rules established here are:

- no-tile streams publish one column and one row to VDPU383;
- tile widths and heights are CTU counts, not `minus_one` values;
- `reg130` CABAC base is zero, `global_len` is `0xc`, and the RCB registers use
  offset/length pairs from the upper layout;
- scaling lists use 1360-byte slots selected by `sps_id` or
  `pps_id + 16`; the VDPU383 table stores all six 32x32 matrices in its
  block-column-major layout;
- the 176-byte H.265 packet is intentionally larger than the VDPU34x 112-byte
  packet and must not be negotiated as a variable payload.

The LTR row has eight SPS long-term entries and repeatedly selects
`lt_idx_sps=4` or `7`; both decoders output all 500 frames with the same hash.
The missing-reference row deletes the sixth AUD-delimited access unit from a
12-picture x265 stream. C reports `Could not find ref with POC 5`; both decoders
publish five frames with the same hash. This closes the H.265 core path with
DSLICE, both scaling-list localities, SPS long-term references and one real
error path, not the complete RK3576 H.265 surface.

A 16-cell deterministic corruption matrix now covers SPS/PPS/SEI flips,
start/middle/end payload flips in the IDR and selected P slices, and three
final-access-unit truncation lengths. Fourteen cells match C's output count
and planar YUV byte for byte. Damaged SPS and a flip at the first IDR slice
payload leave C waiting until timeout; Rust terminates promptly with zero
output. The reproducible gate is
`scripts/board_rk3576_h265_corrupt_vs_mpp.sh`. Wider conformance remains open.

## Rust VDPU383 AV1 bring-up

The first VDPU383 AV1 C-ABI layer is now present in `src/hal/av1d383.rs`.
It serializes the same 5160-bit global header as
`vdpu38x_av1d_uncomp_hdr()`: the `mpp_put_bits` 64-bit little-endian packing,
128-bit alignment and the extra 16-byte trailing reservation are all
reproduced.

On lf1, a patched official C HAL emitted thirteen 672-byte headers for the ten
displayed frames of `av1_tiles_320x240_10.ivf`. The first keyframe matches Rust
byte for byte with SHA-256
`5dc26be2b7f1d2a76d135b64435c737cd62d8b6c2ab720a0fb83c83efddfbf56`
(FNV `0x8da389d2e180d680`). The reproducible C dump patch is
`scripts/av1_vdpu383_dump.patch`.

The same first-keyframe C dump also pins the 212-word serialized
`Vdpu383RegSet`: control/statistic words, tile strides, eleven RCB base/length
pairs, and the current/error/global/output/CDF/colmv addresses all match.

The VDPU383 default CDF image is generated by
`tools/gen_av1_vdpu383_cdf.py` from the C
`g_av1d_default_prob[7400]` table. It is 29,600 bytes with SHA-256
`43474cb59fa76fa1ed95cbfb2fb46952b061e948a13581c04380e51d099c100b`.
At 320x240 the planned buffers are 32,672 bytes working CDF, 3,072 bytes
segmentation, 20,480 bytes colmv and 72,448 bytes RCB.

The first real hardware job now decodes the fixture's keyframe through the
RkvDec client. The output stride follows C's
`mpp_align_128_odd_plus_64()` and is 448 bytes for a 320-pixel picture.
Stock C MPP and Rust both emit 320x240 YUV420p with SHA-256
`6f5b544f53584c7de6d3acad5f4611ca2ee3d75ae259ab981ffca5e599b1b9fe`.
The reproducible gate is `scripts/board_rk3576_av1_vdpu383_key.sh`.

The complete ten-frame reference sequence is now byte-identical to C. Each
persistent frame owns output, colmv and working-CDF DMA, while the session keeps
the eight reference slots and C's `ref_info_tbl[].cdf_valid/coeff_idx` state.
This preserves the primary reference's coefficient-CDF partition across inter
pictures; using the current frame's `base_q_idx` instead first diverged on the
fourth coded job.

All ten visible Y/U/V frames total 1,152,000 bytes with SHA-256
`9d339ae3c5b270ac9059548da0d3ff5ef6cb0c94a9bcb11f5bfc93783e868138` on both
decoders. The full gate is
`scripts/board_rk3576_av1_vdpu383_sequence.sh`.

VDPU383 10-bit output now uses MPP's 704-byte packed stride and 337,920-byte
frame allocation for 320x240. Rust reads that surface as packed NV12 and emits
planar little-endian u16 Y/U/V. The ten-frame output is 2,304,000 bytes with
SHA-256
`f3b69b61a06d3967a89b91f11f56883588df53974d4a1b5efb8fbd9e004d49b8`,
byte-identical to C's skip-grain output; the gate is
`scripts/board_rk3576_av1_vdpu383_10bit.sh`.

FGS remains a hardware boundary. C never enables the VDPU383 FGS block.
Programming `av1_fgs_en`, a packed FGS table, and the FGS base in either raster
or tile mode produces STATUS `0x00000000` followed by a decoder reset. The
verified implementation therefore retains C's skip-grain behavior.

## Rust VDPU383 VP9 bring-up

The VDPU383 VP9 matrix is **7/7** on lf1. The regular rows match the installed
C MPP byte-for-byte; the two known C defects retain the libvpx adjudication:

- profile 0 64x64, 12 frames
- profile 2 10-bit 64x64, 12 frames
- lossless 320x240, 12 frames
- profile 2 10-bit lossless 320x240, 12 frames
- error-resilient 2-column tiles, 640x360, 12 frames
- 720p error-resilient temporal segmentation: Rust == libvpx; C differs
- lossless 321x241: Rust/libvpx produce 2 frames; C produces 1

The bring-up established VDPU383-specific details. The 168-byte global header
is packed separately from the register file and the tile widths are CTU counts,
not `CTU count / 8`. The key-frame probability FIFO is 1312 bytes and the C
writer intentionally truncates the final zero-padded tail. RCB has eleven
VDPU383 regions with refined sizes, while `reg181`/`reg182` select the two
segment maps and the colmv buffer is the uncompressed `width * height / 2`
surface.

`scripts/board_rk3576_vp9_vs_mpp.sh` is the reproducible lf1 gate. The release
LTO compiler on lf1 currently SIGSEGVs in LLVM; the functional gate therefore
uses the debug build and makes no throughput claim.

The Rust-native backend uses the client-20 VPU720 register window, the
384-byte transformed Y/U/V quantization table, and the hardware status length
as a byte count (the C field name contains `bits`, but the HAL adds it to a
byte length). Marker and quantizer generation are shared with the existing
VEPU2 Rust implementation. A shared input-layout model derives packed versus
planar storage size, U/V offsets, chroma stride and UV-swap. VPU720 then
programs source formats 4/5/6/7/8/9/10/12/13 as selected by the C
setup-format switch. The output mode is likewise taken from the C switch:
400/420/422/444. C's upper-chroma output modes are byte-matchable but currently
produce a short 623-byte stream from the NV12 fixture, so the matrix records
behavior rather than claiming useful 4:2:2/4:4:4 content.

`scripts/board_rk3576_jpege_vs_mpp.sh` is the reproducible lf1 gate. It covers
all non-tile 8-bit YUV planar, semi-planar, packed and luma-only inputs tested
through the C probe, plus all four output chroma modes. Tile input remains.
Low-delay is not a pending feature: the VPU720 HAL exposes null
`part_start`/`part_wait`, and the reference probe spins on zero-length packets.
C's VPU720 HAL has no RGB input case and no rotation register field, so Rust
rejects RGB, rotation and low-delay explicitly.

The debug `cargo test --all-targets` gate passes **1175 / 0 failed / 37
ignored** on lf1. The packed YUYV/UYVY hardware test also passes when run
explicitly.

The Rust path writes the 36-byte SPS/PPS prefix, allocates input, output, FBC
reconstruction, thumbnail and anti-smear buffers, submits the six captured
register windows, polls each job and reads the payload length from
`bs_lgth_l32`. The P job alternates the FBC reconstruction, thumbnail and smear
slots, reads slot zero as reference, and switches the captured syntax/AQ/SQI
words to their P-picture values. Across the six-frame cell, reconstruction,
thumbnail and smear use two slots in alternating order. `frame_num` is the
picture index, POC LSB is twice that index, and the observed SQI row alternates
with the slot parity. Run:

```bash
BOARD=luck2 ./scripts/board_rk3576_h264e510_vs_mpp.sh
```

One platform difference was made explicit in the shared SPS writer: RK3588's
2024 library writes `log2_max_mv_length=16`, while RK3576's 2025 library writes
15. `EncoderConfig::vui_log2_max_mv_length` now carries that choice; VEPU510
uses 15. The CBR path reuses `rc_model_v2`, feeding it back with the hardware
payload bits, `qp_sum` and intra-block counts, then programs the VEPU510 RC,
ROI and threshold words. VBR and AVBR use the same hardware mapper with their
respective model allocators. Legacy ROI metadata is mapped directly to the
hardware region words. `setup_vepu510_split` now covers BY_CTU and BY_BYTE in
both one-AU and LOWDELAY output. The low-delay path enables `slen_fifo` /
`vslc_done_en`, drains VEPU510's 8-entry slice FIFO through `POLL_HW_IRQ`, and
uses the 31-bit length plus bit-31 last word. BY_CTU=96 emits 8 packets and
BY_BYTE=256 emits 40 packets across two pictures; both the complete streams and
the packet-length sequences match C. GDR suppresses the IGOP IDR, clamps the
CIME search axis to one line on refresh pictures, resends SPS/PPS at each
recovery boundary and carries the P-frame smear state. The C HAL's ROI base
table is not reachable without QPMAP (`adr_roir` remains zero), so the Rust path
implements the observable semantics rather than retaining dead table setup.
row=2/GOP4 and column=4/GOP6 match complete streams and every picture length.
H.265 VEPU510 starts with the same 320x240 QP26 Main IDR. Its generated field
map has 730 named fields across the same six write windows and a 76-word SQI
view. The C hardware payload is 4440 bytes and the software parameter-set/SEI
prefix is 270 bytes, for a byte-identical 4710-byte packet. RK3576 differs from
the RK3588 H.265 header configuration in three places: `max_cu_size=32`, one
extra transform-tree level, and `cu_qp_delta_enabled=1` even for fixed QP.
The second picture uses the captured P register view and the opposite
recon/colmv/thumb/smear slots, reading slot zero as its reference; the IDR+P
cell is byte-identical at 6810 bytes. Across six pictures the two slot sets
alternate by frame number. Only POC LSB advances in the syntax words, and
`smear_load_en` turns on from the second P picture; the GOP6 stream is
byte-identical at 16994 bytes. CBR reuses `rc_model_v2` with 300/250/350 kbps,
QP bounds 15/10..51 for I/P and an I/QP delta of four. The traced QP trajectory
is `26/29/29/30/30/32`; CBR6 is byte-identical at 11192 bytes. VBR and AVBR
switch only the model allocator and SEI mode; their QP trajectories are
`26/29/29/30/30/30` and `26/29/33/33/33/33`, with byte-identical 11795-byte
and 9676-byte streams. Slice splitting uses the VEPU510 32x32 grid; BY_CTU=8
and BY_BYTE=256 are byte-identical at 7922 and 8264 bytes. Their low-delay
paths produce 20 and 25 packets with identical per-packet lengths.
GDR suppresses IDRs at IGOP boundaries, advances POC continuously, resends an
81-byte parameter-set prefix plus an 8-byte recovery SEI on recovery pictures,
and rotates the smear load/store flags by GOP position. The C VEPU510 ROI base
table remains unused on this path. Row and column cells are byte-identical.
ROI uses the same common VEPU510 four-word region mapping as H.264. A
forced-intra absolute-QP30 region at `(0,0,160,120)` is byte-identical over two
pictures.
10-bit is not supported by the lf1 C HAL: format setup reports
`unsupport frame format` / `invalid src color space: 16` and emits zero bytes.
The Rust entry point performs the same rejection before allocating DMA buffers
or starting a hardware session.
Tiles are also a platform boundary. The 2025 C PPS auto-tile branch covers
RK3566, RK3568 and RK3588 only. On RK3576, an `AUTO_TILE=1` probe produces the
same 4710-byte IDR stream as the ordinary path, while Rust's
`open_tile_columns(2)` rejects before DMA or hardware allocation. This closes
the VEPU510 H.265 functional/boundary matrix at **15/15**.

## Rust capability parity scope

The acceptance target is the full official MPP capability surface exposed on
RK3576, not merely opening `/dev/mpp_service`:

| Path | Required implementation | Required evidence |
|---|---|---|
| H.264 decode | VDPU383 address/RCB/common registers, SPS/PPS/RPS/scan-list packing | byte-exact frames against C MPP |
| H.265 decode | VDPU383 address/RCB/common registers and HEVC table layout | byte-exact Main/Main10/tiles/WPP/720p/DSLICE/SPS-PPS-scaling, 500-frame LTR and missing-reference matrix |
| VP9 decode | VDPU383 probability, segmentation and colmv lifetimes | byte-exact profile 0/2, 8/10-bit, lossless, tiles and known-C-bug adjudication |
| AV1 decode | VDPU383 PicParams/header/global-model and film-grain paths | byte-exact key/inter/film-grain matrix |
| AVS2 decode | VDPU383 AVS2 register path | conformance stream required before claiming support |
| H.264 encode | Fixed-QP IDR/GOP, CBR/VBR/AVBR, ROI, GDR, slice split and LOWDELAY packets at 320x240 are byte-identical; tiles pending | byte-identical streams and STATUS fields |
| H.265 encode | VEPU510 32-CU Main header, six-window IDR/P, two-slot GOP, CBR/VBR/AVBR, slice split, GDR and ROI are implemented; 10-bit and multi-column tiles are explicit platform rejects | byte-identical fixed GOP, RC, packet, GDR and ROI matrices; matched 10-bit/tile rejection gates; full STATUS fields for remaining features |
| JPEG encode | VPU720 packet and register path | 19/19 YUV input/output/geometry matrix byte-identical; tile input pending |
| JPEG decode | RK3576 rkjpegd path | byte-exact output |
| VDPP2 | RK3576 post-processing command/register path | output comparison with C MPP |

Unsupported codec paths must be represented in the SoC capability matrix and
rejected before submission. They are not silently routed through VDPU2 or an
RK3588 register builder.
