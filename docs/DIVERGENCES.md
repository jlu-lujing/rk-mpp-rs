# Known divergences from the C reference

Scope rule (2026-11-02): pixel/byte-exact imitation plus output-preserving
performance. A difference is a defect **unless the C behaviour has been proven
wrong**. This file is the register of every difference that is currently known,
with its disposition and the evidence behind it. New work should close an entry
here before adding capability.

Dispositions:

- **FIX** - ours is wrong or unproven; the C result is the target.
- **C-BUG** - the C result is proven wrong by an independent decoder/spec check;
  ours is kept and the evidence is recorded.
- **NO-ORACLE** - the C vintage cannot produce the comparison at all; not claimed.
- **BY-DESIGN** - a deliberate, documented difference in *behaviour* (exit code,
  recovery) that does not change decoded pixels for valid streams.

## Decoders

| Case | Disposition | Evidence |
|---|---|---|
| H.264 1920x800 `/tmp/demo_short.264`, frames 18+ | **FIXED** | Rust and software FFmpeg agreed on frames 0-17, then diverged in 402 of 600 frames while C matched software 600/600. Root cause was `frame_num` wrap: the stream uses `log2_max_frame_num = 4`, so the counter wraps at 16, and two places compared the raw `frame_num` instead of FrameNumWrap (`frame_num_offset + frame_num`). §8.2.5.3 eviction dropped frame 0 of the new epoch instead of the genuinely oldest frame 15, and §8.2.4.2's initial P list put the older picture at `ref_idx` 0. The scene is nearly static, so the wrong reference produced ±1 errors that then propagated. `FrameStore` now records the epoch, eviction and P-list ordering use FrameNumWrap, and two unit tests pin both. Rust is now byte-identical to C **600/600** (MD5 `c69b9476…f462`), and the stream is back in the fair performance set. |
| AV1 64x64 | **C-BUG** | The rkvdec job never reports done (status `0x1`; a good job reports `0x1100`), so C emits ten all-zero 64x64 pictures (61,440 bytes, 0 non-zero). libaom decodes real content; this crate reports `FRAME_ERR_DEC_HW_ERR` and writes nothing instead of black. 96x96 and up complete normally. |

| H.263 field-coded PAFF | **NO-ORACLE** | No stream in the corpus. |
| AVS+ | **PARTIAL** | RK3588 client 12 and two public 352x288 fixtures are byte-exact across their raw 7/6-frame and full C-default IEP2-vproc 9/7-frame I/P/B cycles through both the Rust CLI and public SDK. | H.264/H.265 FFmpeg second GOP | **C-BUG / NO-ORACLE** | On a cold RK3588, repeated 120-frame/GOP60 H.264 encodes produced four streams across eight fresh processes (`0c9e7106…`, `d7aba365…`, `cc460bf5…`, `38c89798…`); decoding three of those variants produced three different YUVs. | H.265 first tiled picture of a session | **NO-ORACLE** | The reference has no session-independent result.
