# Fixture sources

`SHA256SUMS` locks every file in this directory. Regenerate it only after an
intentional fixture update:

```bash
scripts/update_fixture_hashes.sh
cargo test --test fixture_manifest
```

## Project-generated codec streams

- `av1_*`, `film_grain_10bit.ivf`, `vp8_*`, `vp9_*`, `m2v_*`, `mp4_*` and
  `h263_*` are generated by `scripts/gen_corpus.sh` with FFmpeg's
  `libaom-av1`, `libvpx`, `libvpx-vp9`, `mpeg2video`, `mpeg4` and `h263`
  encoders.
- `av1_lr_320x240.ivf` is two frames of FFmpeg `testsrc2` encoded by libaom
  `aomenc` with 64x64 superblocks, CDEF and loop restoration enabled, and
  palette/intra-BC disabled:
  `--good --cpu-used=0 --end-usage=q --cq-level=20 --passes=1 --limit=2
  --width=320 --height=240 --fps=2/1 --i420 --sb-size=64
  --enable-restoration=1 --enable-cdef=1 --enable-palette=0
  --enable-intrabc=0 --tune-content=film`. The first keyframe exercises
  SGRPROJ restoration after deblocking/CDEF.
- `h264_i32_*` and `h264_i64_*` are local x264 CAVLC streams with FFmpeg
  yuv420p golden output. Their exact generating parameters are recorded in
  `ROADMAP.md` next to the pixel gates.
- `h264_i16_cabac*` and `h264_i4x4_cabac*` are local x264 CABAC streams with
  FFmpeg yuv420p golden output. The fixtures are tiny, deliberately textual
  pictures that isolate I16 DC/AC, chroma residual, multi-macroblock state and
  I4x4 transmission order.
- The `h264_i16_cabac_2x2*` pair is a 32x32, one-frame Main-profile gradient
  encoded with `cabac=1:keyint=1:bframes=0:8x8dct=0`; the `_nodeblock` pair
  adds `no-deblock=1`. Both contain four I16x16 macroblocks and exercise
  top-neighbour propagation across macroblock rows.
- `h264_i8x8_cabac` is a 16x16 one-frame High-profile gradient encoded with
  `cabac=1:keyint=1:bframes=0:8x8dct=1` at QP20. It isolates four I8x8 luma
  transforms, category-5 significance/last contexts and the CABAC 8x8 scan.
- The `h264_cabac_mixed_2x2*` pair expands that same High-profile gradient to
  32x32. Its first row is I8x8 and second row I4x4, so it exercises mixed
  macroblock-type contexts, transform8x8 neighbour selection and top-right
  availability across macroblock boundaries. `_nodeblock` adds `no-deblock=1`.
- The `h264_cabac_two_slices*` pair splits the same 32x32 picture into two
  CABAC slices with `first_mb_in_slice=0/2`. The second I4x4 slice therefore
  exercises CABAC restart, slice-local syntax availability and DC-128
  prediction at the slice boundary. `_nodeblock` adds `no-deblock=1`.
- `h264_i_pcm_cabac` is a 16x16 High-4:4:4-Intra `qp=0` CABAC stream using
  100% I_PCM macroblocks. It locks the raw 4:2:0 sample payload, byte
  realignment and arithmetic-decoder restart behavior.
- `h264_i_pcm_cabac_10bit` repeats the I_PCM gate as 10-bit 4:2:0 and stores
  FFmpeg's little-endian `yuv420p10le` output.
- `h265e_c_fixqp_*` are short fixed-QP streams emitted by the source-built C
  MPP encoder used as the H.265 header oracle.

## C MPP captures

- `av1_cdf/`, `av1_picparams/`, `av1_film_grain/`, `vp9_p*_hw/`,
  `vp8/c_*`, `rc_data_c_probe.txt`, `rc_model_v2_c_*`, `vepu580_*` and
  `p_slice_mmco.264` are captured from the source-built C MPP reference by the
  board scripts under `scripts/board_*`.
- These captures are oracle data, not normal application inputs. Regenerate
  them with the corresponding board script, not by editing bytes manually.

No large third-party conformance suite is stored here. The repository keeps
small project-generated or C-MPP-captured vectors and their hashes; external
corpora remain outside git and are referenced by the board scripts.
